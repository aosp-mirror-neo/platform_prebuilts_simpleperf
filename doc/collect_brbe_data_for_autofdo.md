# Collect BRBE data for AutoFDO and BOLT

## Introduction

The ARM Branch Record Buffer Extension (BRBE) provides a branch record buffer for sampling control
path history in a low-cost manner. It provides source and destination addresses for a sequence of
taken branches, allowing profiling tools to reconstruct parts of the executed control flow.
BRBE data contains branch records, similar to Last Branch Records (LBRs) on x86 architectures.

Simpleperf supports collecting BRBE data and converting it to input files for
[AutoFDO](https://github.com/google/autofdo), which can then be used for Profile-Guided
Optimization (PGO) during compilation.

Collected BRBE data can also be used as input for
[BOLT](https://github.com/llvm/llvm-project/tree/main/bolt).

BRBE data collection requires:
-   an Arm CPU implementing BRBE
-   firmware configuring higher exception levels to permit kernel access to BRBE
-   kernel support for BRBE through the perf subsystem
-   permission to access the corresponding perf events

A sampling event, such as `cpu-cycles`, determines when a sample is generated. When branch stack
sampling is enabled by the `-b` or `-j` option, the sample includes recently executed branches
provided by BRBE through the `PERF_SAMPLE_BRANCH_STACK` interface.

## Enable BRBE data collection

BRBE data collection requires kernel support and appropriate firmware configuration. Before control
is passed to the Linux kernel, the firmware or boot environment must satisfy the BRBE requirements
defined by the arm64 boot protocol.

### Firmware requirements

See `Documentation/arch/arm64/booting.rst` in the Linux kernel source tree for the complete
requirements.

### Enable BRBE in the kernel

Mainline Linux kernels support BRBE from 6.17. `CONFIG_ARM64_BRBE` must be enabled.
```config
CONFIG_ARM64_BRBE=y
```

## Recording BRBE data

The `simpleperf record` command is used to profile processes and store the profiling data in a file
(by default `perf.data`).

The `-j` and `-b` option enable taken branch stack sampling. BRBE data collection is supported for
both userspace and kernel space.
For supported branch filter options check the `simpleperf record --help` command.

```sh
$ adb shell
(device) / $ cd /data/local/tmp

# Do a system-wide collection.
# Root privileges might be required.
(device) /data/local/tmp $ simpleperf record -e cpu-cycles -b -a --duration 3

# For a standalone binary the following command may be used:
(device) /data/local/tmp $ simpleperf record -e cpu-cycles -b ./<binaryname>
```

## Using the recorded data

In order to process the recorded data with optimization tools, it needs to be converted to a
suitable format for the given tool.
The `simpleperf inject` command is used to convert the recorded data. The default output file is
`perf_inject.data`.

Several output formats are supported.

See the documentation of the `simpleperf inject` command for details.

### Converting BRBE data for AutoFDO (userspace binaries)

The recorded data can be converted to a suitable format for
[AutoFDO](https://github.com/google/autofdo).

```sh
(device) /data/local/tmp $ simpleperf inject -i perf.data --binary <binaryname>
```

The `perf_inject.data` file is generated by the above command.

AutoFDO is the default format, so adding `--output autofdo` is not required.

The format is described below:

```autofdo format
<number of executed ranges>
<start>-<end>:<count>
...

<number of sampled addresses>
<address>:<count>
...

<number of branches>
<from>-><to>:<count>
...
// build_id: ...
// binary name
...
```

Since AutoFDO only accepts one binary at a time, use the `--binary` option to restrict the
generated data to the binary being profiled.

Then AutoFDO can be used to generate a profile.

### Converting BRBE data for BOLT (userspace binaries)

The recorded data can be converted to a suitable format for
[BOLT](https://github.com/llvm/llvm-project/tree/main/bolt).

**Note**: BOLT requires the input binary to have an unstripped symbol table. For best results, the
binary should also be linked with relocations (`--emit-relocs` or `-q`).

```sh
(device) /data/local/tmp $ simpleperf inject -i perf.data --binary <binaryname> \
                           --output bolt -o perf_inject_bolt.data
```

The `perf_inject_bolt.data` file generated by the above command is in the `bolt` format.

The format contains `F` and `B` records, followed by the binary's `build_id` and path preceded by
`//`:

```text
F <range_start> <range_end> <count>
B <branch_source> <branch_target> <count> [mispred_count]
```

An `F` record represents an inferred fall-through execution range:

```text
F <range_start> <range_end> <count>
```

It describes sequential execution between branch records, where `count` is the number of times the
range was inferred to have executed.

A `B` record represents an observed taken branch:

```text
B <branch_source> <branch_target> <count> [mispred_count]
```

where `count` is the number of times the branch was observed. If available, `mispred_count`
contains the number of branch mispredictions.

For example:

```text
F 1134 1148 4524
B 1148 1134 4600 0
// build_id: 0xca5e30d1da40e9762bf7cedc14cbfc9500000000
// /data/local/tmp/brbe_test_loop
```

The `F` record represents sequential execution from `0x1134` to `0x1148`, while the `B` record
represents a taken branch from `0x1148` to `0x1134`.

The output may contain records for multiple binaries:

```text
F/B records for binary1
// build_id for binary1
// name for binary1

F/B records for binary2
// build_id for binary2
// name for binary2

...
```

Since BOLT processes one binary at a time, use the `--binary` option to restrict the generated data
to the binary being optimized.

Lines beginning with `//` also need to be removed before further processing with `perf2bolt`.

### (Optional) Converting BRBE data into an intermediate branch-list format

The recorded `perf.data` files can contain additional information (such as timestamps, mmap
records, etc.) not required by later processing based on branching information.
To reduce the amount of data that needs to be stored or transferred for later branch-profile
processing, `perf.data` can be converted to the intermediate `branch-list` format, which may be
used as an input for further conversions with `simpleperf inject`.

```sh
(device) /data/local/tmp $ simpleperf inject -i perf.data --binary <binaryname> \
                           --output branch-list -o branch_list.data
```

**Note**: When processing profiles on the host, `binary_cache_builder.py` can be used to collect
the binaries referenced by `perf.data` into a `binary_cache` directory. It can pull binaries from
the device or locate matching unstripped binaries in host directories specified with `-lib`. This
can simplify symbol resolution when processing recordings containing multiple binaries.

## A complete example: brbe_test_loop.cpp

`brbe_test_loop.cpp` is provided as an example program to show the complete process.

The source code is in [brbe_test_loop.cpp](../runtest/brbe_test_loop.cpp).

The build script is in [Android.bp](../runtest/Android.bp).

The build produces the `brbe_test_loop` executable, which runs on the target device.

The following steps describe how to build and record the example and how to use AutoFDO and BOLT
with the generated data.

**Step 1: Build `brbe_test_loop` binary**

```sh
(host) <AOSP>$ . build/envsetup.sh
(host) <AOSP>$ lunch aosp_arm64-trunk_staging-userdebug
(host) <AOSP>$ make brbe_test_loop
```

**Step 2: Run `brbe_test_loop` on the target device, and collect BRBE data while it runs**

```sh
(host) <AOSP>$ adb push out/target/product/generic_arm64/system/bin/brbe_test_loop /data/local/tmp
(host) <AOSP>$ adb shell
(device) / $ cd /data/local/tmp
(device) /data/local/tmp $ chmod a+x brbe_test_loop
(device) /data/local/tmp $ simpleperf record -e cpu-cycles:u -j any,u ./brbe_test_loop
simpleperf I cmd_record.cpp:882] Recorded for 0.0456293 seconds. Start post processing.
simpleperf I cmd_record.cpp:985] Samples recorded: 78. Samples lost: 0.
```

### Generating an AutoFDO profile for brbe_test_loop.cpp

The following steps describe how to generate an AutoFDO profile from the data recorded above.

**Step 3: Convert BRBE data to AutoFDO input**

```sh
# Option A) Converting to autofdo format on the target device:
(device) /data/local/tmp $ simpleperf inject -o perf_inject_brbe_test_loop.data \
                           --binary brbe_test_loop
(device) /data/local/tmp $ exit
(host) <AOSP>$ adb pull /data/local/tmp/perf_inject_brbe_test_loop.data

# Option B) Using the intermediate branch-list format:
(device) /data/local/tmp $ simpleperf inject -i perf.data --binary brbe_test_loop \
                           --output branch-list -o branch_list.data
(device) /data/local/tmp $ exit
(host) <AOSP>$ adb pull /data/local/tmp/branch_list.data
# Build simpleperf tool on host.
(host) <AOSP>$ make simpleperf_ndk
(host) <AOSP>$ simpleperf inject -i branch_list.data -o perf_inject_brbe_test_loop.data \
               --symdir out/target/product/generic_arm64/symbols/system/bin

# The result should look like:
(host) <AOSP>$ cat perf_inject_brbe_test_loop.data
7
10d4-10f4:4
10d4-111c:1
1108-111c:61
1108-1120:1
1124-1148:4
1134-1148:4524
1134-114c:4
2
1108:1
1134:72
5
10f4->1124:4
111c->1108:63
1120->10d4:1
1148->1134:4600
114c->10d4:4
// build_id: 0xca5e30d1da40e9762bf7cedc14cbfc9500000000
// /data/local/tmp/brbe_test_loop
```

**Step 4: Use AutoFDO tools**

Now `create_llvm_prof` from AutoFDO can be used to generate a profile:

```sh
(host) <AOSP>$ create_llvm_prof -profile perf_inject_brbe_test_loop.data -profiler text \
               -binary out/target/product/generic_arm64/symbols/system/bin/brbe_test_loop \
               -out brbe_test_loop.afdo -format extbinary
(host) <AOSP>$ ls -lh brbe_test_loop.afdo
rw-r--r-- 1 user group 411 Sep 25 09:52 brbe_test_loop.afdo
```

**Step 5: Use AutoFDO profile to build optimized binary**

```sh
(host) <AOSP>$ cp brbe_test_loop.afdo toolchain/pgo-profiles/sampling/
(host) <AOSP>$ vi toolchain/pgo-profiles/sampling/Android.bp
# Edit Android.bp to add a fdo_profile module:
#
# fdo_profile {
#    name: "brbe_test_loop",
#    profile: "brbe_test_loop.afdo"
# }
(host) <AOSP>$ vi toolchain/pgo-profiles/sampling/afdo_profiles.mk
# Edit afdo_profiles.mk to add brbe_test_loop profile mapping:
#
# AFDO_PROFILES += keystore2://toolchain/pgo-profiles/sampling:keystore2 \
#  ...
#  server_configurable_flags://toolchain/pgo-profiles/sampling:server_configurable_flags \
#  brbe_test_loop://toolchain/pgo-profiles/sampling:brbe_test_loop
#
(host) <AOSP>$ vi system/extras/simpleperf/runtest/Android.bp
# Edit Android.bp to enable afdo for brbe_test_loop:
#
# cc_binary {
#    name: "brbe_test_loop",
#    srcs: ["brbe_test_loop.cpp"],
#    afdo: true,
# }
(host) <AOSP>$ make brbe_test_loop
```

To verify that `brbe_test_loop.afdo` is used when building `brbe_test_loop`:

```sh
(host) <AOSP>$ gzip -d out/verbose.log.gz
(host) <AOSP>$ cat out/verbose.log | grep brbe_test_loop.afdo
   ... -fprofile-sample-use=toolchain/pgo-profiles/sampling/brbe_test_loop.afdo ...
```

When comparing the disassembly of
`out/target/product/generic_arm64/symbols/system/bin/brbe_test_loop` before and after optimizing
with AutoFDO data, profile-guided differences in code generation, such as branch layout decisions,
can be observed.

**Note**: The `create_llvm_prof` tool can be built from the AutoFDO sources. Follow the
documentation in the autofdo repo.

### B) Using BOLT with BRBE data of brbe_test_loop.cpp

The following steps describe how to use the data recorded above with BOLT.

**Step 3: Convert BRBE data to BOLT input**

```sh
# Option A) Converting to bolt format on the target device:
(device) /data/local/tmp $ simpleperf inject --output bolt -o perf_inject_brbe_test_loop.data \
                           --binary brbe_test_loop
(device) /data/local/tmp $ exit
(host) <AOSP>$ adb pull /data/local/tmp/perf_inject_brbe_test_loop.data

# Option B) Using the intermediate branch-list format:
(device) /data/local/tmp $ simpleperf inject -i perf.data --output branch-list \
                           -o branch_list.data --binary brbe_test_loop
(device) /data/local/tmp $ exit
(host) <AOSP>$ adb pull /data/local/tmp/branch_list.data
# Build simpleperf tool on host.
(host) <AOSP>$ make simpleperf_ndk
(host) <AOSP>$ simpleperf inject -i branch_list.data --output bolt \
               -o perf_inject_brbe_test_loop.data \
               --symdir out/target/product/generic_arm64/symbols/system/bin

# Now it is required to remove comment lines from perf_inject_brbe_test_loop.data, so that it can
# be processed by perf2bolt.
(host) <AOSP>$ sed -i '/^\/\//d' perf_inject_brbe_test_loop.data
# The result should look like:
(host) <AOSP>$ cat perf_inject_brbe_test_loop.data
F 10d4 10f4 4
F 10d4 111c 1
F 1108 111c 61
F 1108 1120 1
F 1124 1148 4
F 1134 1148 4524
F 1134 114c 4
B 10f4 1124 4 0
B 111c 1108 63 0
B 1120 10d4 1 0
B 1148 1134 4600 0
B 114c 10d4 4 0
```

**Step 4: Generate the BOLT profile and optimize the binary**

Now `perf2bolt` can be used to prepare the generated data for processing with `llvm-bolt`, then an
optimized binary can be generated.

These steps require the unstripped version of the profiled binary to be available on the host.

```sh
(host) <AOSP>$ <LLVM_BIN>/perf2bolt --pa -p perf_inject_brbe_test_loop.data -o perf.fdata \
               ./brbe_test_loop_unstripped
# --no-huge-pages and --align-text=0x4000 are used to avoid generating big binaries due to
# alignment. See https://github.com/facebookarchive/BOLT/issues/138.
# However, if the original binary is built with huge page alignments (-z max-page-size=0x200000),
# then don't use these flags.
(host) <AOSP>$ <LLVM_BIN>/llvm-bolt ./brbe_test_loop_unstripped -data=perf.fdata \
               -reorder-blocks=ext-tsp -reorder-functions=hfsort -split-functions \
               -split-all-cold -split-eh -dyno-stats --no-huge-pages --align-text=0x4000 \
               -o brbe_test_loop.bolt
```

The optimized binary is `brbe_test_loop.bolt`.

**Note**: It can be stripped before deployment.
